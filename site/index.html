Daemonitor is a local Activity Monitor for Gradle and Bazel builds.

Download desktop app Install CLI

macOS · Windows · Linux

Daemonitor is like Activity Monitor for local build processes — Gradle daemons, wrappers, Kotlin daemons, and workers alongside Bazel servers, tests, and workers — with RSS, CPU, heap, and uptime on the machine where the build runs.

Live observation is zero-lock for Bazel (never calls bazel info / dump). The CLI is a Native Go binary with no JDK; the desktop app is a separate packaged JVM application for the same local core. History stays in SQLite on your disk.

Gradle history comes from daemon logs (including IDE or agent source). Bazel history is opportunistic when a build already emits local BEP — Daemonitor never enables BEP itself. Laptop or SSH; no cloud account.

Go read the CLI options for more, or grab packages from GitHub Releases. Gradle and Bazel share Live Monitor, Visual timelines, Build History, and the CLI hierarchy.

What Daemonitor shows

Live Monitor

Desktop Live Monitor lists Gradle daemons, wrappers, Kotlin daemons, and workers alongside Bazel servers, tests, and workers — with RSS, CPU, uptime, and memory-pressure badges.

Visual timelines

Memory, CPU, I/O, and GC modes with live / 15m / 1h windows so concurrent Gradle and Bazel processes are easy to compare.

Build History

Recent Gradle builds with duration, outcome, peak resources, and coding-agent attribution. Filter by tool for opportunistic Bazel BEP rows when your builds already write them.

CLI

Bubble Tea TUI over SSH or on headless machines. Native Go binary; starts daemonitor-cored when needed and does not require a JDK. The desktop app remains a separate packaged JVM application. Press v to group descendant workers under their daemon or Bazel server; h/l fold or expand a group while keeping individual process rows available.

  • Live process table with RSS, heap, CPU, and uptime
  • Grouped Gradle daemon and Bazel server hierarchy with fold/expand controls
  • Shares the desktop app’s local database and retention settings

Privacy

Local-first by design. History and process data stay on your computer.

  • No telemetry — nothing is phoned home about your builds or machine.
  • Local SQLite storage — history lives in a database on your computer.
  • Best-effort redaction — command lines and logs are redacted before storage.
  • Local read-only MCP — agent access stays on localhost and cannot mutate builds.

MCP

Optional local, read-only MCP so compatible tools can inspect retained build history and currently visible Gradle and Bazel processes — without leaving the machine.
